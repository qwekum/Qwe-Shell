# Workspace redesign — 2026-09-10

This redesign follows the user's quiet, premium Windows desktop brief and
three-pane reference. It supersedes the earlier interface's layout direction;
the earlier review scores do not qualify this new work.

## Current implementation addendum — 2026-09-12

The implemented workspace has advanced beyond the 2026-09-10 evaluation
artifact. The center pane now shows source-backed **Entry details** rather than
the earlier passive property relationship map. Each editable property opens the
native expression editor for its actual declaration span. Captured system
entries show rule, property, source, effective `settings.modify`, and
completeness evidence; quick edits create or reuse a context-scoped managed
rule, while **Open shared rule** is the explicit route to a wider handwritten
rule. Unresolved or stale source associations remain readable and read-only.

Actual-menu capture also materializes retained submenu semantics automatically
through the native popup constructor. The semantic hierarchy does not depend on
scrolling or hovering every submenu. Captured pixels remain separate appearance
evidence, and an opened popup can add observed appearance without replacing its
semantic descendants. Commands are never invoked during discovery; rejected
side effects, unsupported functions, provider failures, cycles, and capture
bounds leave explicit incomplete branches. These additions have local source,
fixture, and offscreen evidence in [local-verification.md](local-verification.md),
but no post-change live Explorer or human acceptance record.

## Assessment and direction

The previous interface separated menu structure, property inspection, and
expressions into competing surfaces. A large undifferentiated menu area,
repeated property buttons, strong borders, and unresolved expression labels
made startup feel unfinished. The new direction organizes the actual editing
work around the menu itself, source-backed entry details, and an inspector. The default
left pane is a menu preview; an explicit Arrange entries view retains structural
drag-and-drop editing. Captured pixels and their entry hit targets are separate
from the source-safe edited preview. Missing native appearance is disclosed.

Entry details show source properties and open the real expression editor.
It is not a runtime evaluator or a fabricated capture. Native and custom menu
entries, rule scope, original snapshots, capture cancellation, undo/redo,
templates, settings, tools, and reviewed application remain available.

Segoe UI, a restrained blue accent, white/light-gray working surfaces, subtle
structural dividers, and stronger interactive outlines establish the light
theme. A deliberate dark palette shares the same semantic tokens. Standard
Windows window chrome remains intact. High-contrast mappings remain separate
from the designed palettes. There are no decorative metrics, marketing panels,
fake live previews, or new UI frameworks.

All six files under `docs/configuration` were reviewed against this direction.
`properties.html` distinguishes shortcuts, radio/check marks, default entries,
separators, visibility, and icon sources. `themes.html` includes fonts, spacing,
RTL, gradients, transparency, and acrylic effects. This is why a structural
reconstruction cannot be labeled an exact runtime appearance: captured popup
pixels carry that appearance, while source previews remain explicitly labeled.
`index.html` and `new-items.html` also require nested partial imports to remain
available during configuration inspection.

The existing configuration-only view still collects imported definitions rather
than reproducing every import-site placement. It is not the exact-menu view;
the captured runtime menu supplies ordering, nesting, and evaluated appearance.
The nested-import resolver repair preserves access to these definitions without
claiming full source-to-runtime preview parity.

## Choosing a context

The workspace context picker distinguishes a folder itself, empty space inside
a folder, the desktop background, files, and drives. Common file groups appear
before the general file choice. A group can be narrowed to one extension, and
the file/folder chooser can restrict capture acceptance to one concrete target.
The picker describes where to right-click after capture is armed. It does not
open a context menu or execute a configuration expression.

Studio's file type group settings let the user edit the names and extensions of
the groups and add or remove groups. These versioned, bounded preferences are
stored separately under the user profile, outside the Shell configuration.
Picking an umbrella group filters incoming captures; it does not widen saved
rules to every extension in that group. Recorded captures remain inspectable
without requiring their historical paths to exist. Mismatched captures preserve
the current menu and pending edits.

implementation against the complete brief. Passing requires at least 8/10.
Below that score, revise and review again, up to three evaluations total.
The third score and unresolved issues are retained regardless of result.

## Verification boundary

The verification plan includes populated and empty states, long text, errors,
minimum window size, light/dark/high-contrast mappings, keyboard interactions,
and real property-editing actions. Rendered bitmaps and offscreen tests do not
qualify physical DPI, OS text scaling, Narrator, live Explorer capture, or human
acceptance. No Computer Use or active desktop system changes are part of this
redesign workflow.
